## 手を動かして確認したこと

| 予想 | 実行したこと | 結果から分かったこと |
|---|---|---|
| `drwxr-xr-x`では所有者だけが項目を追加できる | 資料を見ずに、所有者・グループ・その他の利用者ができる操作を説明した | `r`を一覧表示、`x`を項目への到達として区別できた。`w`は項目の追加に加えて削除や名前変更にも関係する |
| systemdがservice定義に従ってプログラムを起動し、OSがPIDを割り当てる | 資料を見ずに起動の流れと`ps`、`top`、`pgrep`の用途を説明した | serviceは起動を管理し、OSがプロセスを識別するPIDを割り当てる。三つの調査方法を用途で区別できた |
| `task vm:status`はVMを起動する可能性があると考えた | service状態を確認する前に、表示内容と状態変更の有無を予想した | Hono APIのservice名、`Active`、`Main PID`と、状態確認・状態変更の違いが次の学習対象だと分かった |
| 状態確認はVMやserviceを起動しないと説明を受けた | `task vm:status`を実行し、`sakaguchi-app.service`の`Active`と`Main PID`を確認した | VMへ接続でき、Hono APIを管理するserviceが実行中で、中心となるプロセスのPIDが存在する |
| `task`の役割は分からなかった | `Taskfile.yml`に登録された`vm:ssh`がLimaの接続操作を呼び出すと確認し、`task vm:ssh`を実行した | `task`は登録済み操作を呼び出し、`vm:ssh`ではserviceを変更せずVMへ接続できる |
| `pgrep`でNode.jsプロセスを一行に絞れると予想した | 引用符を閉じ忘れて`>`の入力待ちになった後、`Ctrl-C`で取り消し、正しいコマンドを再実行した | 最初の「表示なし」はプロセス不在ではなかった。`pgrep`のPIDはMain PIDと一致し、起動内容は`/usr/local/bin/node src/server/index.ts`だった |
| 教材では短いプロセス名が`node`だと想定していた | `ps -C node`を実行し、見出しだけになる現象を確認した。次にMain PIDを直接指定し、短いプロセス名と起動内容を確認した | 短いプロセス名は`MainThread`であり、`-C node`では一致しない。PIDを指定すると、利用者、資源使用量、状態、起動内容を確認できた |
| プロセス表示だけでは、どのserviceが起動したかを断定できないと考えた | `systemctl cat sakaguchi-app.service`で`User`、`WorkingDirectory`、`ExecStart`を確認した | service定義、Main PID、実プロセスの利用者と起動内容を照合する必要がある |
| 対話的な接続は終了操作が必要だと確認した | 観察後に`exit`を実行してLima VMからホストへ戻った | SSH接続の終了はserviceを停止せず、観察前のホスト側へ戻る操作である |
| 状態確認とVM接続は再実行できるが、プロセス調査コマンドは不安だった | 資料を閉じて`task vm:status`と`task vm:ssh`を再実行し、`pgrep`と`ps`は実行前に分からないと申告した | `task`による状態確認と接続は定着した。`pgrep`と`ps`は目的と書式を結び直す必要がある |
| 複雑な検索条件を一度に読むのは難しかった | 教材を`pgrep -af node`で候補を表示し、起動内容を目で確認する手順へ簡略化した | まず候補を出し、`src/server/index.ts`を含む行を選んでからPIDを`ps -p`へ渡せばよい |
| `ps`にも対象を絞る機能があると気づいた | `pgrep -af node`と`ps -p`の役割を比べた | `pgrep`はPIDが分からない段階で候補を検索し、`ps -p`は見つけたPIDの詳細を表示する。どちらも対象を絞れる |
| オプションと表示項目の調べ方が分からなかった | `ps --help list`と`ps --help output`を使った | `-p`は対象PID、`-o`は表示する列を指定する。ヘルプは目的別に選べる |
| 完全な`ps`コマンドにはヒントが必要だった | 対象PIDへ`user`、`pid`、`pcpu`、`pmem`、`stat`、`args`を指定して詳細を表示した | 実行利用者、CPU、メモリ、待機状態、起動内容を正しく読み、`pgrep`との役割の違いも説明できた |
| 資料なしでプロセス調査を再実行できると予想した | Node.jsプロセスの候補を検索し、対象PIDを選んで標準表示と必要な列の指定を行った | PID、利用者、CPU、メモリ、待機状態、起動内容を確認できた。`pgrep`による検索と`ps`による詳細確認を資料なしで再現できた |
