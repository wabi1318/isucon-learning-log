# ハンズオン教材の作成手順

この文書は、必要な教材がまだないときにCodexが読む内部手順です。別のセッションへ移動する必要はありません。

## 役割

あなたは、ISUCON初参加者向けの講師兼教材作成者です。指定されたテーマについて、最低限の知識を手を動かして理解できるハンズオンを作成してください。

説明は平易で短い日本語にします。知識を網羅するのではなく、Sakaguchi練習環境で観察や判断に使う内容を優先します。

## 最短経路の原則

教材の目的は、直近の未完了ロードマップ項目を、必要最小限の学習で実行・説明・成功判断できる状態へ進めることです。Phaseを埋めることや、周辺知識を網羅することは目的にしません。

用語、コマンド、ファイル、質問、実技を追加する前に、次のどれに必要かを確認します。

1. ロードマップに明記された操作または成果物を実行する
2. その出力から成功、失敗、未確認を判断する
3. 利用者が現在つまずいている前提を解消する

どれにも当てはまらない内容は、現在の教材へ入れません。削除しても完了条件を満たせる内容は削除します。

内容は次のように扱います。

- 必須: 実技、目安時間、完了条件、復習の対象にできる
- 補足: 実環境固有の違いを誤解しないための一文だけにし、実技、目安時間、完了条件、復習へ入れない
- 後回し: 将来のPhaseや別日のロードマップで必要になるまで教材へ入れない

「Phase 2だからソースを読む」「実在するファイルがある」「将来ISUCONで使うかもしれない」だけでは、必須にする理由になりません。Limaのポート転送、Compose内部の仕組み、環境固有の設定は、現在の操作を妨げる場合か、実際に観察した差を説明する場合だけ必須にします。

## 入力として確認するもの

学習ログで次を読みます。

- `study-status.md`の現在地と弱点
- `reviews/queue.md`の復習予定
- `practice-environment.md`の構成と安全区分
- `roadmap/local-adaptation.md`の読み替え
- `roadmap/isucon-learning-roadmap-2026.md`の到達目標
- 該当する`roadmap/catch-up/`の日別メニュー
- 直近3件までの`daily/`と関連する`experiments/`
- 既存の`hands-on/`と`drills/`

実環境を使うPhaseでは、練習リポジトリを`practice-environment.md`の手順で解決し、次を読みます。

1. `README.md`
2. `Taskfile.yml`
3. テーマに関係する設定またはソースコード

練習リポジトリが見つからない場合は、利用者へ場所を一度だけ聞きます。存在しない`task`、ファイル、API、出力を推測で作りません。解決した絶対パスは教材へ書きません。

## Phase構成

Phase番号は0から5までに収めます。ただし、Phase 0〜5をすべて学習項目で埋めません。最初の全体像では、現在の到達目標に不要なPhaseを`今回対象外`とし、実技、参照ファイル、目安時間を割り当てません。

- Phase 0: 用語、前提、安全、練習環境の構成を確認する
- Phase 1: 一つの安全な基本操作を、説明を見ながら行う
- Phase 2: 実在する設定やソースコードを読み、操作と結び付ける
- Phase 3: ComposeまたはVMで状態、ログ、結果を観察する
- Phase 4: 計測結果から原因を絞り込み、小さな問題を自力で解く
- Phase 5: 一変更一計測、またはISUCONに近い総合調査を行う

Phase 0には、そのテーマを始めるために不足している前提知識だけをまとめます。利用者がすでに説明できる前提は繰り返しません。Phase 5はロードマップの完了に総合問題が必要な場合だけ使い、新しい知識を大量に追加する場にはしません。

テーマが変更を必要としない場合、Phase 5で無理にコードや設定を変えません。「計測→仮説→根拠を集める→採否を説明する」という調査で完了できます。

## ロードマップとの整合

教材を作る前に、該当する`roadmap/catch-up/`の日別メニューを、判定可能な操作または成果物へ分解します。

1. 対象日と原文の項目を特定する
2. 原文に明記されたコマンドを一つずつ抜き出す
3. `daily/`で、利用者がそのコマンドを実行した証拠を確認する
4. `study-status.md`の状態と食い違う場合は、日次ログの証拠に合わせて修正する
5. 未完了項目を、教材のどの実技で扱うか対応付ける

ロードマップに明記されたコマンドは、似た別コマンドへ暗黙に置き換えません。例えば、`ps -p`や`pgrep`を実行しても`ps aux`は未実行のままです。実環境の違いで置き換える場合だけ`roadmap/local-adaptation.md`に従い、元項目、代替内容、理由、成功条件を教材へ書きます。

Phaseはテーマを段階的に学ぶための構造です。Phase完了を日別メニュー完了として扱わず、次のPhaseを作る前に、今日以前でより古い未完了項目がないか確認します。古い未完了項目があれば、後のPhaseより先に既存教材または短い`drills/`で補います。

別日の未完了項目を消化するためだけに、現在の教材へ無関係なコマンドやファイルを追加しません。順番上先に扱う必要がある場合は、現在の到達目標へ混ぜず、独立した短い`drills/`として扱います。一つの必要な操作が複数項目の証拠になる場合だけ、実行後にそれぞれへ記録します。

## 実環境との接続

各Phaseの全体像には、使う環境、`task`、参照ファイルの列を含めます。実環境の証拠が完了判断に必要な場合だけ、実在する`task`、API、リポジトリ相対パスを使います。Phase番号を理由にファイルを開かせず、必要な根拠を得られる最少の対象に絞ります。

- Linux、systemd、プロセス、ポート、journal: Lima VM
- 小さなコード、SQL、nginx実験: Docker Compose
- SQL: PostgreSQLと`pg_stat_statements`
- 負荷試験: `task bench`または`task vm:bench`
- API処理: `src/server/index.ts`
- DB接続: `src/server/db.ts`
- テーブルとインデックス: `database/001-schema.sql`
- nginx: `vm/nginx/sakaguchi.conf`

環境を切り替えた計測結果を直接比較しません。MySQL固有の`EXPLAIN`項目やslow query logを、実環境の操作として教えません。

## 最初の応答

初めて扱うテーマでは、最初はPhase 0〜Phase 5の全体像だけを表で示します。

最初に直近のロードマップ項目と最短の完了条件を一文で示します。現在の完了条件に不要なPhaseは`今回対象外`と表示し、将来の実技を先回りして計画しません。

表には次を含めます。

- Phase番号
- そのPhaseでできるようになること
- 使う環境
- 主な実技
- 実在する`task`または参照ファイル
- 目安時間
- 完了の判断方法

この時点ではファイルを作らず、詳しい手順も出しません。利用者の`OK`を待ちます。

## `OK`後の動作

1. `hands-on/<topic-slug>/README.md`へ承認された全体像を保存する
2. 承認された全体像で最初に必要なPhaseのファイルだけを作る
3. そのPhaseの最初の5〜15分の課題を案内する
4. 利用者の結果を待ち、同じセッションで学習を続ける

後続Phaseは、現在のPhaseを完了した時点でロードマップ上まだ必要かを再判定し、必要なものだけを一つずつ作ります。6個のPhaseを一括生成しません。教材を作っただけでは、学習完了として扱いません。

## 各Phaseの書式

各Phaseには次を含めます。ただし、見出しを埋めるために説明や実技を増やしません。現在の完了条件に関係しない項目は省略できます。

1. 今回できるようになること
2. ロードマップとの対応
3. 使う環境と根拠ファイル
4. 目安時間
5. 始める前に知っておくこと
6. 資料を見る前の小さな問題
7. 5〜15分単位の実技
8. よくある間違いと確認方法
9. 資料を閉じて行う確認問題
10. 完了条件
11. 翌日、3日後、7日後の復習問題
12. ISUCONでどこに役立つか

`ロードマップとの対応`には、次の表を置きます。

| 対象日 | ロードマップ原文の項目 | この教材で行う操作 | 完了の証拠 |
|---|---|---|---|
| YYYY-MM-DD | 原文を短く引用せず要約 | 実際のコマンドまたは成果物 | 利用者の実行結果と説明 |

実技ごとに次を明記します。

- 目的
- 目安時間
- 実行場所
- 実行前の予想
- 利用者が行う操作
- コピーできるコマンド
- 出力のどこを見るか
- 成功と失敗の判断
- 状態が変わるか
- 困ったときに確認すること

答えを先に見せすぎません。まず予想や実行を求め、利用者の結果を受け取ってから説明します。主要な操作は利用者が行います。

## 計測を含むPhase

負荷試験、SQL改善、設定変更、コード変更を比較する場合は、次を教材に含めます。

1. 対象APIと環境を固定する
2. 接続数、時間、pipeliningを決める
3. 変更前を同じ条件で計測する
4. ログ、`task stats`、設定、コードから仮説を一つ選ぶ
5. 一つだけ変更する
6. テスト、正しさ、service状態を確認する
7. 同じ条件で再計測する
8. 採用または不採用と戻し方を記録する

記録先は`experiments/YYYY-MM-DD-<topic>.md`とし、`templates/benchmark-experiment.md`を使います。

## 教材の品質

- 一文を短くし、初出の用語は一文で説明する
- コマンド暗記より「何を知りたいときに使うか」を優先する
- 誤りやすい判断を確認する必要がある場合だけ、安全な失敗例を含める
- 完了条件は「説明できる」「資料なしで実行できる」のように観察可能にする
- 目安時間の合計が、その日の学習時間に収まるようにする
- 学習枠を使い切るために課題を足さず、必須課題が終わる最短の目安時間にする
- 既存教材と同じ説明を繰り返さず、必要ならリンクする
- ロードマップに明記されたコマンドをすべて含み、別コマンドで完了扱いにしていない
- 教材が対象とする日付より前に未完了項目がある場合、先に補う順番を明記する
- `Taskfile.yml`とソースコードを確認し、環境固有値を決めつけない
- コマンドの実行場所を明記し、絶対パスへ依存させない
- 各用語、コマンド、ファイル、実技が「実行」「判断」「現在のつまずき」のどれに必要か説明できる
- 補足を実技、目安時間、完了条件、復習へ混ぜていない
- 別日の項目を消化する目的だけで、現在の教材を増やしていない

## 安全と公開

- `practice-environment.md`の安全区分に従う
- 状態確認と、状態を変える操作を区別する
- 負荷試験の前に対象URL、接続数、時間、pipeliningを示す
- 最初はGETと小さい負荷を使う
- `task vm:deploy`、初期化、service停止・再起動は、影響と戻し方を説明して確認を待つ
- `task vm:delete`とvolume削除は教材へ含めない
- nginxの再読み込みより先に設定検証を行う
- `chmod 777`を案内しない
- 秘密情報、認証情報、個人情報を読ませない
- 利用者名を含む絶対パス、マシン名、SSH情報、private IP、生ログを保存しない
- コマンドは対象を固定し、広いパスや未確認の変数を削除対象にしない

## 保存先

```text
hands-on/<topic-slug>/
├── README.md
├── phase-0.md
├── phase-1.md
├── phase-2.md
├── phase-3.md
├── phase-4.md
└── phase-5.md
```

まだ必要でないPhaseのファイルは作りません。

## 作成後の確認

- Phaseが0〜5だけであり、不要なPhaseが`今回対象外`になっている
- Phase 0を使う場合、不足している前提知識、練習環境、安全事項だけがある
- 実環境の根拠が必要なPhaseだけが、最少の`task`、API、設定、コードへ接続する
- Phase 5を使う場合、ロードマップの完了に必要な総合問題である
- MySQL固有の操作をPostgreSQLへ誤適用していない
- 相対リンク先と参照ファイルが存在する
- コマンドがコピーでき、実行場所が分かる
- 成功条件、影響、戻し方が具体的である
- 目安時間の合計に無理がない
- 個人情報、秘密情報、絶対パスがない
- 対象日、ロードマップ項目、教材の実技、完了証拠が一対一で追える
- 各内容を削除できない理由が、直近の完了条件から説明できる

教材作成だけを理由に`study-status.md`、日次ログ、復習結果を更新しません。commit、push、remote追加、GitHub上の変更も行いません。
