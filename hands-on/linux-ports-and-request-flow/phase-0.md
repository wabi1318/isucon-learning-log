## 予想後に説明する前提知識

### クライアントとHTTPリクエスト

クライアントは、Webサーバーへ処理を依頼する側です。ブラウザや`curl`が送る依頼をHTTPリクエストと呼びます。

### プログラム、プロセス、PID

nginxとNode.jsはプログラムです。プログラムを実行し、OSが管理している動作中のものをプロセスと呼びます。動作中のnginxとNode.jsは別のプロセスで、OSがそれぞれを区別するためにPIDを付けます。

### ポート

ポートは、一つのマシン内で通信の受付先を区別する番号です。PIDが動作中のプロセスを区別する番号なのに対し、ポートは通信の宛先を区別します。

### 待受状態

プロセスが特定のIPアドレスとポートで接続を受け付けられる状態を、待ち受けていると表現します。`ss -lntp`ではTCPの待受状態が`LISTEN`として表示されます。

### nginx、Node.js、リバースプロキシ

Sakaguchi練習環境では、nginxが外側からHTTPを受け付け、`/api/`へのリクエストをNode.jsへ渡します。このように、リクエストを受けて別の処理先へ渡す役割をリバースプロキシと呼びます。

Node.jsはHono APIを動かし、nginxから渡されたリクエストを処理します。二つが別のポートを使うため、同じVM内でも通信の受付先を区別できます。

nginxでは転送先のまとまりを`upstream`として名前付けできます。現在の設定は転送先が一つなので、複数のNode.jsへ負荷を振り分けてはいません。

### 想定される通信経路

設定ファイルから、次の順番が想定されています。

```text
クライアント
  → Lima VMの:80
  → nginxのプロセス
  → 127.0.0.1:3000
  → Node.jsのプロセス
  → Hono API
```

補足として、この練習環境ではLimaがホスト側の`:18080`をVM側の`:80`へ転送します。この仕組みはPhase 0の完了条件には含めません。

## 実技1: 役割を分ける

- 目的: プロセスと通信の宛先を混同しない
- 目安時間: 3分
- 実行場所: Codexとの会話
- 実行前の予想: PIDとポートのどちらがプロセスを区別するか考える
- 利用者が行う操作: `プロセス`、`ポート`、`nginx`、`Node.js`を一文ずつ説明し、クライアントから届いたリクエストを誰が受けて誰が処理するかを答える
- コマンド: なし
- 出力のどこを見るか: なし
- 成功の判断: PIDとポートの役割を分け、nginxが受け付けと転送、Node.jsがAPI処理を担当すると説明できる
- 失敗の判断: PIDとポートを同じ番号として扱う、またはnginxとNode.jsを同じプロセスとして扱う
- 状態が変わるか: 変わらない
- 困ったとき: 「何を識別する番号か」と「HTTPを最初に受けるのは誰か」を分けて考える

## 実技2: 通信経路を矢印で書く

- 目的: ポート番号を暗記せず、通信の順番と役割を結び付ける
- 目安時間: 2分

- 実行前の予想: 外側からHTTPを最初に受けるのはnginxとNode.jsのどちらか考える

- コマンド: なし

- 失敗の判断: `:80`と`:3000`を同じ受付先として扱う
- 状態が変わるか: 変わらない
- 困ったとき: nginxは外側から受け取り、Node.jsへ転送する

## よくある間違いと確認方法

| 間違い | 確認方法 |
|---|---|
| PIDとポートを同じ番号だと考える | PIDはプロセス、ポートは通信の受付先を区別する |
| ポートが単独で通信を処理すると思う | そのポートで待ち受けるプロセスがあるか確認する |
| nginxがHono APIの処理を行うと思う | nginxは受け付けと転送、Node.jsはAPI処理を担当する |
| 設定にポートが書かれていれば実際に待ち受けていると思う | Phase 1で`ss -lntp`を実行して確認する |

## 資料を閉じて行う確認問題

1. PIDとポートは、それぞれ何を区別する番号か説明する。
2. 待受ポートとは何か説明する。
3. nginxとNode.jsが、HTTPリクエストに対してそれぞれ何を担当するか説明する。
4. クライアントからnginxの`:80`、Node.jsの`:3000`までを矢印で書く。
5. 設定を読んだだけでは、実際に待ち受けていると断定できない理由を説明する。

## ISUCONでどこに役立つか

ISUCONでは、リクエストが届かない場合に、nginxが待ち受けていないのか、Node.jsが待ち受けていないのか、転送先が違うのかを順番に確認します。プロセスとポートを区別できれば、推測で設定を変更せず、通信が止まっている場所を証拠から絞れます。
