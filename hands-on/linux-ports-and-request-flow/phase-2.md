## 資料を見る前の小さな問題

設定を開く前に、現在の理解で答えます。

1. nginxは`:80`で受け取ったAPIリクエストを、次にどこへ渡すと思いますか。
2. Node.jsが待ち受けるポートは、どのファイルで確認できると思いますか。
3. 設定に`:80`や`:3000`が書かれていることと、`ss`で`LISTEN`が表示されたことは、何が違うと思いますか。

分からないものは「分からない」と答えて構いません。予想後に、一つずつ設定を開きます。

## 始める前に知っておくこと

### 三種類の根拠

| 根拠 | 分かること | 分からないこと |
|---|---|---|
| 設定ファイル | 起動したときに使う予定のポートと転送先 | 現在、本当に待ち受けているか |
| `ss -lntp` | 現在待ち受けているIPアドレスとポート | `Process`欄が空の場合、その所有プロセス名 |
| プロセス表示 | 現在動いているプログラムとPID | そのプロセスがどのポートを所有するか |

複数の根拠が同じ構成を示すほど確度は上がります。ただし、表示されていない情報を推測だけで断定しません。

### `less`の基本

`less FILE`はファイルを変更せず、画面ごとに内容を読みます。

- `/文字列`とEnter: 下方向へ検索する
- `n`: 次の一致へ移動する
- `q`: `less`を終了する

Phase 2では編集操作を行いません。

## 実技1: nginxの待受先と転送先を読む

- 目的: nginxが受け取るポートとNode.jsへ渡すポートを設定から確認する
- 目安時間: 5分
- 実行場所: 練習リポジトリのルート
- 実行前の予想: `listen`と`server 127.0.0.1`に続く番号を考える
- 利用者が行う操作: SSH接続を終了し、nginx設定を`less`で開いて待受先と転送先を見つける
- コマンド:

現在のVM接続を終了します。VMやserviceは停止しません。

```sh
exit
```

練習リポジトリのルートへ戻ったら実行します。

```sh
less vm/nginx/sakaguchi.conf
```

`listen`、`server 127.0.0.1`、`proxy_pass`を確認し、`q`で終了します。

- 出力のどこを見るか: `listen`、`upstream sakaguchi_app`内の`server`、`proxy_pass`
- 成功の判断: nginxが`:80`で待ち受け、APIを`:3000`へ渡す設定を説明できる
- 失敗の判断: `listen`と転送先の`server`を同じ役割だと捉える
- 状態が変わるか: SSH接続は終了するが、VMとserviceは動いたまま。ファイル内容は変わらない
- 困ったとき: ファイル全体を保存せず、探している設定名だけを伝える

## 実技2: Node.jsの待受ポートを読む

- 目的: nginxの転送先とNode.js側の待受設定が一致するか確認する
- 目安時間: 5分
- 実行場所: 練習リポジトリのルート
- 実行前の予想: `PORT`が未指定の場合の番号を考える
- 利用者が行う操作: Node.jsのソースを`less`で開き、ポート設定を検索する
- コマンド:

```sh
less src/server/index.ts
```

`less`の画面で次を入力します。

```text
/const port
Enter
```

`process.env.PORT`と既定値を確認し、`q`で終了します。

- 出力のどこを見るか: `const port =`の行と、ファイル末尾の`serve`呼び出し
- 成功の判断: `PORT`が未指定の場合は`:3000`を使い、nginxの転送先と一致すると説明できる
- 失敗の判断: 設定の既定値だけで、実際の待受状態まで断定する
- 状態が変わるか: 変わらない
- 困ったとき: `q`で終了し、検索文字列が見つかったかだけを伝える

## よくある間違いと確認方法

| 間違い | 確認方法 |
|---|---|
| nginxの`listen 80`とNode.jsの`:3000`を同じ待受先だと考える | 受付側と転送先を矢印で結ぶ |
| 設定に書かれた値を現在の状態だと断定する | `ss`の`LISTEN`と別々に記録する |
| `Process`欄が空でも所有プロセス名を断定する | プロセス名は別の証拠が必要だと記録する |
| `less`から戻れずシェルが止まったと思う | `q`で終了する |

## ISUCONでどこに役立つか

ISUCONでは、設定ファイルだけを見て正常と判断せず、実際の待受状態やプロセスと照合します。根拠の種類を分けられれば、通信経路のどこに追加調査が必要かを明確にできます。
