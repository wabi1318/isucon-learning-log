## 始める前に知っておくこと

### プログラム、プロセス、service

| 用語 | 意味 | Sakaguchi練習環境での例 |
|---|---|---|
| プログラム | 実行する処理がファイルとして用意されたもの | Node.jsと`src/server/index.ts` |
| プロセス | プログラムを実行したときに、OSが管理する一つの動作単位 | Node.jsがAPIを処理している状態 |
| service | systemdが長時間動かすプロセスの起動方法や再起動方法を管理する単位 | `sakaguchi-app.service` |

同じプログラムを二つ起動すると、プロセスも二つできます。serviceはプロセスそのものではなく、プロセスをどの利用者で、どの場所から、どのコマンドで起動するかを管理します。

Sakaguchi練習環境の`vm/systemd/sakaguchi-app.service`には、次の対応が定義されています。

| 設定 | 確認できること |
|---|---|
| `User=sakaguchi` | プロセスを動かす利用者 |
| `WorkingDirectory=/opt/sakaguchi/current` | 起動時のカレントディレクトリ |
| `ExecStart=/usr/local/bin/node src/server/index.ts` | 起動するコマンド |
| `Restart=always` | 終了した場合にsystemdが再起動する設定 |

### PIDと主な表示項目

PIDは、現在動いているプロセスを区別する番号です。同じプログラムから複数のプロセスが作られても、動いている間はPIDで一つずつ区別できます。プロセスが終了し、再び起動するとPIDが変わることがあります。

| 項目 | 意味 | 最初に確認すること |
|---|---|---|
| `USER` | プロセスを動かしている利用者 | service定義の`User`と一致するか |
| `PID` | 動いているプロセスを区別する番号 | 調査対象の番号はどれか |
| `%CPU` | CPUをどの程度使っているか | 他のプロセスより大きいか |
| `%MEM` | メモリをどの程度使っているか | 他のプロセスより大きいか |
| `STAT` | 実行中、待機中などの状態 | 先頭の文字は何か |
| `COMMAND` | 起動したプログラムと引数 | 調べたいプログラムか |

`STAT`の先頭が`R`ならCPU上で実行中、`S`なら処理を待っている状態です。サーバープロセスはリクエストを待つ時間が長いため、`S`だけを根拠に異常とは判断しません。

### 三つの調査方法

| コマンド | 見え方 | 向いている目的 |
|---|---|---|
| `ps aux` | 実行した時点の一覧 | 全体を一度確認し、結果を見比べる |
| `pgrep -af PATTERN` | 名前や起動内容に一致する行だけ | Node.jsなど対象を絞ってPIDと起動内容を確認する |
| `top` | 一定間隔で更新される一覧 | CPUやメモリ使用率の変化を観察する |

`top`は`q`で終了します。プロセスのコマンド引数に秘密情報が含まれる場合があるため、全行をそのまま記録または共有せず、必要な対象と列だけを要約します。

## 実技2: 調査方法を選ぶ

- 目的: 知りたいことに応じて`ps`、`top`、`pgrep`を選ぶ
- 目安時間: 5分
- 実行場所: Codexとの会話
- 実行前の予想: 「一覧」「絞り込み」「変化」のどれが必要かを先に決める
- 利用者が行う操作: 次の三つの場面に合うコマンドを一つずつ選び、理由を書く
- コマンド: なし
- 出力のどこを見るか: なし
- 成功の判断: コマンド名だけでなく、選んだ理由を説明できる
- 失敗の判断: 三つを同じ用途として扱う
- 状態が変わるか: 変わらない
- 困ったとき: 表示を一度残したいのか、対象を絞りたいのか、変化を見続けたいのかを考える

場面:

1. Node.jsのプロセスが存在するか、対象を絞って確認したい。
2. CPU使用率が時間とともにどう変わるかを観察したい。
3. 現在動いているプロセス全体を一度表示して見比べたい。

## 実技3: プロセス表示を読む

- 目的: 一行の表示から、誰が何を動かしているかを読み取る
- 目安時間: 10分
- 実行場所: Codexとの会話
- 実行前の予想: 各列が利用者、識別番号、資源使用量、状態、起動内容のどれかを考える
- 利用者が行う操作: 教材用の表示を読み、下の五問へ答える
- コマンド: なし
- 出力のどこを見るか: `USER`、`PID`、`%CPU`、`%MEM`、`STAT`、`COMMAND`
- 成功の判断: 五つの列を根拠に、対象プロセスを一つ説明できる
- 失敗の判断: `node`という名前だけを見て、利用者やPIDを確認しない
- 状態が変わるか: 変わらない
- 困ったとき: 左から列名と値を一つずつ対応させる

次は教材用の例であり、現在のVMの出力ではありません。

```text
USER        PID %CPU %MEM STAT COMMAND
sakaguchi  2451  1.2  2.0 Ssl  /usr/local/bin/node src/server/index.ts
```

1. このプロセスを動かしている利用者は誰ですか。
2. PIDはいくつですか。
3. CPU使用率とメモリ使用率はいくつですか。
4. `STAT`の先頭文字から、実行中と待機中のどちらだと判断しますか。
5. どのプログラムが、どのコードを動かしていますか。

## よくある間違いと確認方法

| 間違い | 確認方法 |
|---|---|
| プログラムのファイルがあれば動いていると思う | PIDを持つプロセスが存在するか確認する |
| serviceとプロセスを同じものとして扱う | service定義と、実際に動くPIDを分ける |
| PIDをプログラム固有の固定番号だと思う | 再起動後はPIDが変わる可能性を考える |
| `S`を停止や異常だと決めつける | リクエストなどを待っている正常な状態か確認する |
| CPU使用率が高いだけで原因と断定する | 同じ時間のログ、処理内容、他の資源も確認する |
| プロセス一覧をそのまま共有する | 対象行と必要な列だけを要約する |

## 資料を閉じて行う確認問題

目安は10分です。このファイルを閉じて回答します。

1. プログラム、プロセス、serviceの違いを説明する。
2. PIDは何を区別する番号か説明する。
3. `ps`、`top`、`pgrep`を、一覧、変化、絞り込みに対応させる。
4. 教材用の一行から、利用者、PID、CPU使用率、メモリ使用率、状態、起動内容を読む。
5. `STAT`が`S`であることだけでは異常と判断できない理由を説明する。
6. 出力のどこを見て、目的のプロセスだと判断するか説明する。

## 完了条件

次の三つをすべて満たしたらPhase 0完了です。

- 資料なしで、プログラム、プロセス、serviceの違いを説明できる

「読んだ」だけでは完了にしません。実際の回答と資料を閉じた説明を確認した後に、学習状況と日次ログを更新します。

## ISUCONでどこに役立つか

ISUCONでは、ベンチマーカー実行中にCPUやメモリを多く使うプロセスを見つけ、nginx、アプリ、PostgreSQLのどこを次に調べるか決めます。プロセスを正しく読めれば、推測で設定を変更せず、観察した事実から調査対象を絞れます。
