## 実技1: service状態を予想してから確認する

- 目的: コマンドを実行する前に、何を確認するかを決める
- 目安時間: 5分の予想と10分の確認
- 実行場所: 練習リポジトリのルート
- 実行前の予想: Hono APIを管理するservice名と、正常時に見る項目を答える
- 利用者が行う操作: 予想をCodexへ送り、確認後に状態確認コマンドを実行する
- コマンド:

```sh
task vm:status
```

- 出力のどこを見るか: `sakaguchi-app.service`の`Active`と`Main PID`
- 成功の判断: serviceの状態とMain PIDを見つけ、何を表すか説明できる
- 失敗の判断: VMへ接続できない、serviceが`active`ではない、またはMain PIDが見つからない
- 状態が変わるか: 変わらない
- 困ったとき: エラー全文ではなく、VMへ接続できたか、`Active`、`Main PID`だけをCodexへ伝える。`task vm:up`は実行しない

予想すること:

1. Hono APIのNode.jsプロセスを管理するservice名は何だと思いますか。
2. serviceが正常に動いている場合、`Active`にはどのような状態が表示されると思いますか。
3. `Main PID`は何を表すと思いますか。
4. `task vm:status`は状態を変える操作だと思いますか。

## 実技2: Node.jsプロセスの候補から対象を見つける

- 目的: `node`を含む候補だけを表示し、起動内容から対象を見つける
- 目安時間: 10分
- 実行場所: 練習リポジトリのルートからLima VMへ接続した後
- 実行前の予想: どの起動内容が表示されたらHono APIのプロセスだと判断できるか考える
- 利用者が行う操作: VMへ接続し、Node.jsプロセスの候補を表示して起動内容を目で確認する
- コマンド:

```sh
task vm:ssh
```

VMへ接続した後に実行します。

```sh
pgrep -af node
```

`pgrep`は条件に合う実行中のプロセスを探します。`-a`はPIDと起動内容を表示し、`-f`はプログラム名だけでなく起動コマンド全体から`node`を探します。

- 出力のどこを見るか: 候補のうち、起動内容に`src/server/index.ts`がある行と、その行頭のPID
- 成功の判断: 候補を表示し、`src/server/index.ts`を動かす行を起動内容から選べる
- 失敗の判断: 一行も表示されない、または`src/server/index.ts`を含む行がない
- 状態が変わるか: SSH接続とプロセス表示だけで、service状態は変わらない
- 困ったとき: 一行も表示されない場合は追加の操作をせず、`task vm:status`で確認した`Active`と`Main PID`をCodexへ伝える。複数行ある場合は`src/server/index.ts`を含む行だけをCodexへ伝える

## 実技3: 対象プロセスの列を読む

- 目的: PIDだけでなく、誰が何を動かしているかを資源使用量とともに確認する
- 目安時間: 10分
- 実行場所: Lima VMへ接続中のシェル
- 実行前の予想: `USER`はservice定義の`User=sakaguchi`と一致するか考える
- 利用者が行う操作: 実技2で起動内容を確認した行のPIDを使い、対象プロセスだけを表示して各列を読む
- コマンド:

次の`12345`は例です。実技2で`src/server/index.ts`を含む行の先頭に表示されたPIDへ置き換えます。

```sh
ps -p 12345 -o user:20,pid,pcpu,pmem,stat,args
```

- 出力のどこを見るか: `USER`、`PID`、`%CPU`、`%MEM`、`STAT`、`COMMAND`
- 成功の判断: `src/server/index.ts`の行について、六つの項目を自分の言葉で説明できる
- 失敗の判断: PIDだけを見て、利用者と起動内容を確認しない
- 状態が変わるか: 変わらない
- 困ったとき: 対象以外の行やコマンド引数を共有せず、`src/server/index.ts`の行にある必要な列だけを要約する

確認すること:

1. 実行利用者は誰か。
2. `pgrep`で選んだ行と`ps`で見たPIDは一致するか。
3. CPU使用率とメモリ使用率はいくつか。
4. `STAT`の先頭文字は何か。
5. `COMMAND`から、目的のコードを動かしていると判断できるか。

確認後は、次でホストへ戻ります。

```sh
exit
```

## よくある間違いと確認方法

| 間違い | 確認方法 |
|---|---|
| ホスト側の`ps`でVM内のプロセスを探す | `task vm:ssh`でUbuntuへ接続しているか確認する |
| service名を`node`だと思う | `sakaguchi-app.service`とNode.jsプロセスを分ける |
| PIDを固定値として記憶する | 現在の出力から毎回確認する |
| 最初から複雑な条件で一つに絞ろうとする | `pgrep -af node`で候補を表示し、起動内容の`src/server/index.ts`を目で確認する |
| `ps -C node`で対象を探す | この環境の短いプロセス名は`MainThread`なので、`pgrep`で確認したPIDを`ps -p`へ渡す |
| PIDだけで目的のプロセスだと判断する | `USER`と`COMMAND`も確認する |
| `STAT`の`S`を異常と決めつける | リクエストを待っている正常な状態か考える |
| VMが停止中でも先へ進む | `task vm:up`を実行せず、状態確認の結果を共有する |
| プロセス一覧をそのまま保存する | 対象行の必要な列だけを要約する |

## ISUCONでどこに役立つか

ISUCONでは、ベンチマーカー実行中にどのプロセスがCPUやメモリを使っているかを確認します。対象のプロセスを利用者と起動内容から正しく特定できれば、nginx、アプリ、PostgreSQLのどこを次に調べるか判断できます。
